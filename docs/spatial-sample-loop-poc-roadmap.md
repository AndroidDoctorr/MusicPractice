# Spatial Sample Loop PoC Roadmap

This is the implementation companion to
[`spatial-sample-loop-concept.md`](spatial-sample-loop-concept.md). It adds
time-signature support, meter-aware snapping, effect-chain presets, and a
concrete starting structure for the Unity proof of concept.

## Short recommendation

Start with:

1. A data model that stores musical time independently of GameObjects.
2. A DSP-clocked transport that can reliably schedule one bundled sample.
3. One generated ring and one reusable `SampleInstance` view prefab.
4. Runtime creation and pooling of sample views from model instances.
5. Vive grab, move, audition, clone, and delete interactions.
6. Microphone recording only after scheduled playback is stable.

Do not start by building a complete sample store, effects palette, or preset
browser. Use temporary debug controls until the record-place-clone-play loop is
musically reliable.

## Prefab versus programmatic GameObjects

Unity can create the complete sample object in code with `new GameObject`,
`AddComponent`, and a generated `Mesh`. That is useful for prototypes, but it is
not the best boundary for this project.

Use a hybrid approach:

- Create one authored `SampleInstance.prefab`.
- Put stable Unity and SteamVR wiring on the prefab.
- Instantiate or pool it programmatically for every `SampleInstanceData`.
- Generate its arc mesh, waveform, collider dimensions, color, and labels from
  the model at runtime.
- Never create a separate prefab for each recorded sound.

The prefab should be a view, not the saved musical data. Destroying and
recreating every view must leave the loop unchanged.

### Suggested sample prefab

`Assets/Prefabs/v2/SampleInstance.prefab`

Suggested hierarchy:

```text
SampleInstance
  ArcMesh
  Waveform
  LeadingEdge
  TrailingEdge
  SelectionOutline
  Label
```

Suggested root components:

- `SampleInstanceView`
- SteamVR `Interactable`
- `Rigidbody`
- A simple grab collider
- An interaction component that emits semantic edit commands

Suggested child responsibilities:

- `ArcMesh`: procedurally generated wedge or ribbon
- `Waveform`: optional generated line or mesh
- Edge objects: attack/release handles, disabled until selected
- `SelectionOutline`: selection, mute, pending, and error state
- `Label`: sample name and optional pitch

A simple box or curved ribbon is sufficient for the first vertical slice. Do
not delay timing and interaction tests for production-quality mesh generation.

### Objects that should be generated

Generate these from data because their shape or count changes at runtime:

- Ring segments and beat markers
- Bar, beat-group, and subdivision markers
- Playhead position
- Sample arc geometry
- Pattern ghosts and snap previews
- Delay-tap previews
- Sample-instance views

Instantiate these from reusable prefabs or pooled view objects. Avoid saving
runtime-generated instances back into the scene.

### Objects that can remain authored prefabs

- `SpatialLoopRoot`: composition root and calibrated workspace anchor
- `SampleInstance`: reusable visual/interactive shell
- `TransportControl`: start, stop, tempo, count-in, and recenter controls
- `RecorderControl`: microphone state and record interaction
- Later, `SampleBank` and `EffectsPalette` shells

The ring itself can be generated by `LoopRingView` under `SpatialLoopRoot`.
There is no need for a prefab containing a fixed number of beat objects.

## Musical-time model

Do not store event timing as angles, `Transform` positions, seconds, or step
array indexes. Store musical time as integer ticks and derive world positions
from it.

### Recommended representation

Use a fixed resolution such as 960 pulses per quarter note:

```text
Project
  transportTempo
  loops[]
  sampleAssets[]
  effectPresets[]

Loop
  bars
  timeSignature
  tempoBeatUnit
  instances[]

TimeSignature
  numerator
  denominator
  beatGroups[]

SampleInstance
  startTick
  durationTicks
  sampleAssetId
  velocity
  pitchSemitones
  envelope
  effectChain
```

At 960 PPQ:

- Quarter note: 960 ticks
- Eighth note: 480 ticks
- Sixteenth note: 240 ticks
- 4/4 bar: 3840 ticks
- 3/4 bar: 2880 ticks
- 6/8 bar: 2880 ticks

The conversion is:

```text
ticksPerDenominatorUnit = PPQ * 4 / denominator
ticksPerBar = numerator * ticksPerDenominatorUnit
```

Store loop positions modulo `ticksPerBar * bars`. Convert a tick to normalized
ring phase, then to angle and world position. This keeps the model exact while
the view remains continuous.

## Time signatures and beat grouping

A numerator and denominator alone are not enough to display or snap musical
grouping correctly.

Examples:

- 4/4 defaults to groups `[1, 1, 1, 1]`
- 3/4 defaults to `[1, 1, 1]`
- 6/8 defaults to `[3, 3]`
- 9/8 defaults to `[3, 3, 3]`
- 7/8 may use `[2, 2, 3]`, `[3, 2, 2]`, or another user-selected grouping

`beatGroups` are measured in denominator units and must sum to the numerator.
They determine:

- Strong and secondary visual markers
- Metronome accents
- Default snap hierarchy
- Pattern interpretation
- Repeat divisions

### Tempo beat unit

Tempo also needs an explicit beat unit. A BPM value of 120 may mean quarter
notes in 4/4 but dotted quarters in compound 6/8.

Store the transport tempo unit separately:

- 4/4 default: quarter note
- 3/4 default: quarter note
- 6/8 default: dotted quarter note
- 9/8 default: dotted quarter note

Seconds per timeline tick should be derived from BPM and the tempo beat unit,
not directly from the time-signature denominator.

For the first PoC, support:

- 4/4
- 3/4
- 6/8 with `[3, 3]` grouping

The data model should already permit arbitrary numerator, denominator, and
grouping so 5/4 and 7/8 do not require a rewrite.

## Meter- and pattern-aware snapping

Snapping should combine several candidate sources without forcing every edit
onto a 16-step grid.

### Snap candidate sources

1. **Loop boundaries:** start/end and bar starts
2. **Meter groups:** quarter-note beats in 4/4, dotted-quarter groups in 6/8
3. **Denominator units:** eighth-note positions in 6/8
4. **Chosen subdivision:** halves, thirds, quarters, or another division of a
   meter group
5. **Pattern points:** active ghost locations from a template
6. **Existing events:** optional alignment with nearby starts or ends
7. **Free position:** exact unsnapped tick when the modifier is held

### Snap behavior

When an object is dragged:

- Convert its world angle to an unsnapped loop tick.
- Ask each enabled snap provider for nearby candidates.
- Choose the closest candidate inside a configurable magnetic threshold.
- Break ties by priority: bar, meter group, pattern point, subdivision, existing
  event.
- Show a ghost at the selected candidate.
- Highlight the marker that supplied it.
- Provide a short haptic pulse when the selected candidate changes.
- Commit the exact candidate tick on release.

Pattern snapping should be additive. Enabling a House template can make kick,
clap, and hat targets magnetic without hiding the meter grid. Holding the
free-placement modifier bypasses all candidates.

### Pattern roles

Pattern points should identify roles rather than fixed sample slots:

```text
PatternPoint
  tick
  role
  defaultVelocity
  accent
```

Examples of roles are `Kick`, `Snare`, `ClosedHat`, and `OpenHat`. Assigning a
sample asset to a role allows the same template to work with recorded sounds.

The existing patterns in
[`SequencerPattern.cs`](../Assets/Scripts/Instruments/Controllers/Sequencer/SequencerPattern.cs)
can be converted from their 16-step arrays into 4/4 tick positions. New patterns
should be authored in ticks and include their intended meter.

## Saving effect combinations as presets

An effect combination should be data, not a prefab and not a direct collection
of scene components.

### Effect-chain data

Use an ordered chain:

```text
EffectChainPreset
  id
  name
  version
  effects[]
  visualTheme

EffectDefinition
  effectType
  enabled
  wet
  parameters
```

Initial effect types can be:

- Low-pass filter
- Delay
- Reverb send

Each effect type owns a known parameter schema. Avoid arbitrary dictionaries in
the runtime processing path; validate and convert serialized values when loading
the preset.

### Preset scopes

- **Factory presets:** ScriptableObjects checked into the project
- **User presets:** versioned JSON saved with user/project data
- **Project-local presets:** embedded in a saved project when portability is
  important

Applying a preset should copy a snapshot of its values onto the asset, instance,
or loop by default. Later changes to the named preset should not silently alter
existing songs. A future explicit "linked preset" mode can opt into shared live
updates.

### Saving from the spatial interface

The selected object's visible effect satellites represent its current chain.
A "save combination" action should:

1. Capture the ordered chain and parameters.
2. Ask for or generate a name.
3. Create a preset token in the effects palette.
4. Give the token a miniature material preview.
5. Allow grabbing that token and dropping it onto another sample or loop.

Dropping a preset creates a preview first. Commit applies the copied chain;
cancel restores the previous chain.

### Audio-runtime constraint

Pooled voices must have all effect state reset when reused. Otherwise a voice
previously used for a delayed sample can leak settings into an unaffected
sample.

For the PoC, use a fixed supported effect order and adapter components around
Unity's built-in filters or mixer routing. Do not attempt a general plugin chain
before the filter, delay, and reverb workflow has been validated.

## Sample bank and effects palette

These are useful, but they are not the first implementation step.

### Sample bank

Build the sample bank after recording, placement, cloning, and deletion work.
It should be a view over `SampleAsset` data:

- Runtime-generated token per asset
- Token uses the asset's color and miniature waveform
- Grab token to create an instance
- Trigger token to audition
- Deleting the final loop instance does not delete the token

The bank can use one authored shell prefab and programmatically create or pool
its tokens.

### Effects palette

Build the effects palette after one effect can be applied through data:

- Factory effect tokens
- Saved chain-preset tokens
- Drop target for saving a selected object's current chain
- Grab/drop application to assets, instances, or loops

Do not encode the authoritative chain in the palette GameObject. The token is a
view over `EffectChainPreset` data.

## Implementation roadmap

### Milestone 1: musical-time foundation

Build:

- `MusicalTime` conversion helpers
- `TimeSignatureData` with grouping and tempo beat unit
- `LoopData` and `SampleInstanceData`
- Ring phase/angle conversion
- Meter marker generation
- Snap candidates for 4/4, 3/4, and 6/8

Test:

- Exact bar lengths
- Tick/phase/angle round trips
- Wraparound at zero
- Group accents
- Nearest-candidate selection

Exit condition: time, meter, and snapping can be tested without a scene or
GameObject.

### Milestone 2: DSP scheduling vertical slice

Build:

- DSP transport
- Look-ahead scheduler
- Small `AudioSource` voice pool
- One loop using a bundled kick or click sample
- Start, stop, BPM change, and loop restart

Start with a known clip instead of microphone input. This isolates scheduling
bugs from recording bugs.

Exit condition: a four-on-the-floor pattern plays for ten minutes without
accumulated drift, duplicate wrap triggers, or missed events.

### Milestone 3: ring and sample view

Build:

- Dedicated PoC scene and `SpatialLoopRoot`
- Programmatically generated ring and meter markers
- Playhead derived from DSP phase
- One reusable `SampleInstance` prefab
- Programmatic sample-view factory or pool
- Arc mesh driven by start tick and duration
- Trigger emission

Use keyboard or editor debug commands first if that gets the geometry visible
before VR interactions are wired.

Exit condition: changing model timing redraws the sample at the correct angle,
and deleting/rebuilding all views does not change playback.

### Milestone 4: Vive arrangement interaction

Build:

- Grab and move
- Meter-aware snap preview
- Free-placement modifier
- Audition
- Clone
- Delete
- Undo for move, clone, and delete
- Room anchoring and recentering

Exit condition: a player can construct and edit a beat from an existing sample
without a sequencer panel.

### Milestone 5: recording and sample assets

Extract or adapt recording and silence trimming from
[`SamplePad.cs`](../Assets/Scripts/Instruments/Controllers/Sampler/SamplePad.cs)
into a non-singleton capture service.

Build:

- Microphone selection and level feedback
- Hold-to-record
- Non-destructive trim metadata
- Sample-asset creation
- Physical object spawning
- Immediate audition

Exit condition: record-to-placement works without using the old 16-slot pad.

### Milestone 6: meter and pattern workflow

Build:

- Time-signature selection for 4/4, 3/4, and 6/8
- Correct group markers and metronome accents
- Subdivision selection
- House pattern conversion
- Pattern-role assignment
- Ghost targets and pattern-aware snapping

Exit condition: the same placement workflow behaves musically in simple and
compound meter, and a House template accelerates editing without taking control
away from the player.

### Milestone 7: sample bank and loop variations

Build:

- Collapsible sample bank
- Runtime sample tokens
- Two loops sharing sample assets
- Quantized loop switching
- Duplicate-loop variation workflow

Exit condition: a player can create an A/B variation without copying audio or
rerecording samples.

### Milestone 8: effects and effect presets

Build:

- Fixed filter, delay, and reverb data schema
- Runtime application to pooled voices
- Effect satellites and basic visual language
- Factory presets
- Save-current-chain action
- Runtime preset tokens and drag/drop application

Exit condition: effect combinations can be saved, reapplied, and persisted
without leaking settings between pooled voices.

## First implementation slice

The smallest useful first slice is:

1. Add musical-time model and tests.
2. Schedule one existing kick at ticks `0`, `960`, `1920`, and `2880` in 4/4.
3. Generate a one-bar ring.
4. Instantiate four views from one `SampleInstance` prefab.
5. Drive their positions and the playhead from the same model and transport.
6. Add grab-to-move with quarter-note snapping.

That slice proves the core model-view-audio relationship. Recording, stores,
effects, arbitrary meters, and polished visuals can then be added without
rewriting the foundation.

## PoC guardrails

- Do not use scene transforms as saved event data.
- Do not create one prefab or `AudioClip` copy per sample instance.
- Do not use `WaitForSeconds` as the musical clock.
- Do not make the sample bank own sample data.
- Do not make effect-preset tokens own effect data.
- Do not force every meter through a 16-element step array.
- Do not build arbitrary effect/plugin hosting.
- Keep the old machine-based scene intact until the new interaction proves
  itself.
